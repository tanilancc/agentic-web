# Quorum Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Quorum: give it a headcount, dietary needs, a budget and a delivery window; it gets binding quotes from several food vendors, finds the best plan inside those rules, and places the orders the visitor approves.

**Architecture:** Three small vendor sites in `apps/market/` share one pricing module and publish partner desks (the town's pattern). Each vendor's `request_quote` is the only authority on price. Quorum (`apps/quorum/`) searches the vendors' quotes in code across times, pickup or delivery, and one-vendor or split orders; a checker decides which plans fit the mandate. One assistant explains the options, takes changes, asks "what if" quotes, and places the approved orders, each in the vendor's own window.

**Tech Stack:** As the other plans. Reuses `apps/shared/partner-desk.js`.

**Spec:** `docs/superpowers/specs/2026-11-16-agentic-web-trio-design.md`, sections 5 and 8.

## Decisions taken from the spec

- **Spike 4 (spec §9) is decided without a spike:** the negotiation loop runs in code. The design allowed this ("the negotiator's loop moves into site code") and a four-agent loop on a small model cannot be tested here without a key. The assistant keeps the judgement a person needs: which plan, what to change, and the "what if" questions it asks vendors.
- **One front agent** with tools, not four agents: the skill's default, and the search, checker and baseline are code.
- **The baseline and the plan are the same search.** The page shows the cheapest one-vendor plan next to the best plan overall, so a split order must earn its place.
- **Vendors publish only a partner desk and a menu page**, no agent network of their own (cut line; they are demo businesses).

## Global Constraints

- Everything in the earlier plans' Global Constraints applies.
- Prices and totals come only from a vendor's `request_quote`. Plans that fail the checker are never presented as acceptable.
- Every order passes the total the visitor saw; the vendor refuses a mismatch.
- Local origins: Quorum `http://localhost:8094`; vendors `http://127.0.0.1:8095` (Little Oven), `http://127.0.0.1:8096` (Green Fork), `http://127.0.0.1:8097` (Harbour Bakehouse).

## Review Focus

1. **A vendor that is down** during a search: the search finishes with the others and says which vendor did not answer.
2. **No plan fits:** the result says why for the closest plan (over budget by $X, short of N vegetarian servings), never a plan marked acceptable.
3. **A price change between search and order:** that vendor's order is refused with its reason; others stand.
4. **Mandate input at the edges:** headcount 0, more dietary needs than people, a window that ends before it starts, a budget of 0 — refused with a field and a reason.
5. **Hostile text from a vendor menu** is shown as text.

### Task 1: Vendor pricing and three vendors

**Files:** `apps/shared/vendor-pricing.js`; `apps/market/{little_oven,green_fork,harbour_bakehouse}/` each with `catalog.js`, `index.html`, `styles.css`, `partner-actions.js`, `partner-callers.js`, `partner-desk/`, `js/saved-orders.js`; `apps/sites.json`. Tests: `tests/shared/vendor_pricing.test.mjs`, `apps/market/*/tests/partner_actions.test.mjs`.

- Catalog: `{id, name, items:[{id, name, priceCents, serves, diets:["vegetarian"|"vegan"|"gluten-free"]}], minOrderCents, delivery:{feeCents, freeOverCents, leadMinutes}, pickup:{discountPct}, hours:{from, to}, slotMinutes, tiers:[{minItems, discountPct}], offPeak:{from, to, discountPct}}`.
- `quote(catalog, {date, time, fulfilment:"delivery"|"pickup", items:[{id, qty}]}, now) -> {ok:true, lines, subtotalCents, discounts:[{label, cents}], feeCents, totalCents, servings, dietServings} | {ok:false, reason}`. Order of discounts: volume tier, then off-peak, then pickup, each on the running subtotal, rounded to cents.
- Vendors differ: Little Oven (pizza, cheap per serving, strong volume tiers, no gluten-free), Green Fork (salads and bowls, vegan and gluten-free, higher price, off-peak discount), Harbour Bakehouse (sandwich platters, mixed diets, pickup discount, high minimum order).
- Partner actions per vendor: `get_catalog` (read, bridge), `request_quote` (read, bridge), `place_order` (irreversible, top-level; quote args + contact + `expectedTotalCents`; saved to the vendor's storage; refused on mismatch).
- [ ] Tests: each discount and fee rule; refusals (outside hours, under lead time, under minimum, unknown item, qty 0); each vendor's actions as in the town.

### Task 2: Mandate and checker

**Files:** `apps/quorum/js/mandate.js`. Test: `apps/quorum/tests/mandate.test.mjs`.

- Mandate: `{date, headcount, vegetarian, vegan, glutenFree, budgetCents, from, to, flexMinutes, pickupAllowed}`. `validateMandate(m) -> {field, reason}[]`.
- `checkPlan(plan, mandate) -> {ok, problems:[string], slackCents}` where plan is `{orders:[{vendor, time, fulfilment, items, quote}]}`. Rules: servings ≥ headcount; vegetarian servings (vegetarian or vegan items) ≥ vegetarian + vegan; vegan servings ≥ vegan; gluten-free servings ≥ glutenFree; total ≤ budget; every time within `[from - flex, to + flex]`; pickup only when allowed. Each problem names the shortfall with numbers.
- [ ] Tests for each rule, a passing plan, and every Review Focus 4 case.

### Task 3: Basket builder and search

**Files:** `apps/quorum/js/search.js`. Test: `apps/quorum/tests/search.test.mjs`.

- `buildBasket(catalog, need) -> items[]`: cheapest cost per serving that meets the need's diet counts first (vegan, then gluten-free, then vegetarian), then the remaining servings. Pure.
- `searchPlans({vendors, catalogs, mandate, quote}) -> {plans, baseline, failures}`: candidate terms are each slot time in the window (± flex) at `slotMinutes` steps, each allowed fulfilment; candidates are one-vendor plans and two-vendor splits (one vendor covers the diet needs, the other the rest). `quote(vendorId, args)` is the vendor's `request_quote`. Plans are checked with `checkPlan`; sorted by passing first, then total. `baseline` is the cheapest passing one-vendor plan. `failures` lists vendors that did not answer. A cap of 60 quote calls per search, cheapest-first, is stated in the result when reached.
- [ ] Tests with in-memory vendors (the real `quote()` behind a stand-in): the split beats one vendor when diets demand it; off-peak time wins when inside the window; a down vendor is skipped and named; no passing plan returns the closest with its problems.

- [ ] Tests: network valid; a scripted visit sets a mandate, finds the best plan, and places it; no model request holds the card; a hostile item name renders as text; a refused order leaves the other standing.
